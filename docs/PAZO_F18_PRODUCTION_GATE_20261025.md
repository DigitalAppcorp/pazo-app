# F18 — gate de producción preparado, NO ejecutado

Este procedimiento requiere GO explícito del PO para cada ámbito: SQL/Edge/frontend, merge y apertura comercial. La orden de desarrollo no lo otorga. No se modifica PayPal ni se crea una compra como parte del despliegue.

1. Revisar PR/CI, diseño G y manifiesto del mismo commit. Confirmar cero trabajo paralelo que se sobrescriba; conservar los PR históricos. Revisar dependencias SQL y catálogo actual de las funciones que se reemplazan. Mantener el bloqueo de db push/repair: el baseline histórico no es reproducible desde cero.
2. Verificar backup/restore privado vigente y recuperación de operador conforme a F17. No reexportar ni divulgar sus contenidos innecesariamente. Capturar conteos y definiciones afectadas por lectura, no credenciales; la migración no borra registros históricos.
3. Con autorización SQL, ejecutar **solo** la migración F18 revisada, en una transacción, mediante el procedimiento de versión individual auditado del proyecto. Usar los bytes LF de Git indicados en el manifiesto (no la conversión CRLF automática de Windows). Conservar el SHA-256 de bytes y la versión CLI 20261025054548; si el gestor asigna otro ID, reconciliar el archivo al ID real preservando bytes antes de continuar. Nunca instalarla dos veces por timeout: comprobar catálogo/historial primero. Locks limitados a cinco segundos.
4. Postflight: cuatro tablas privadas de promoción + certificado/auditoría con FORCE RLS; ninguna lectura/escritura directa de clientes/servicio; own RPCs solo authenticated y tick/control solo service_role; certificado solo postgres. Compras/invitaciones OFF, certificado false, ledger/owners/consentimientos/holds intactos, viejas RPC comerciales revocadas y solo sus tres triggers de cola deshabilitados. Probar lectura bajo roles; no usar una fila sintética como venta.
5. Con autorización Edge, publicar los tres entrypoints del manifiesto: checkout, worker y `pazo-admin-public-supporter`. Preservar configuraciones JWT y secretos existentes. Comparar **todos** los archivos y hashes de cada clausura de imports con la fuente aprobada; smoke negativo de Auth/origen/MFA y salud. No redeplegar webhook, account ni otros servicios por inercia. No rotar credenciales ni reconfigurar el proveedor.
6. Con autorización frontend, publicar un artefacto revisable del mismo código y verificar rutas PWA/PayPal, UI nueva, recuperación y errores sin crear suscripciones. No activar Git autodeploy ni publicar por merge indirecto. Registrar el deployment exacto y el resultado; un build local no es evidencia hosted.
7. Solo tras verificar el despliegue real, y con ambas pausas, el operador puede ejecutar la función **postgres-only** `supporter_private.certify_public_supporter(commit40, sqlSha256, bundleManifestSha256)`. Usar el commit de código aprobado, hash de bytes SQL real y hash del manifiesto de bundles realmente cotejados. La función no puede ser llamada por browser/service_role, conserva evidencia privada y no habilita publicidad/cobros. Releer registro y salud. Un manifiesto generado localmente no demuestra que la fuente esté instalada.
8. GO comercial nuevo del PO: desde PAZO, administrador con TOTP reciente → PayPal Live → Configuración y controles → Habilitar checkout público → confirmación literal. SQL verifica certificado, salud, merchant original, plan USD2.99, términos y generación antes de escribir estado `public`. No llamar SQL de activación como atajo de MFA. Releer estado efectivo. La publicidad permanece pausada hasta su GO y acción separada; no debe habilitarse para conseguir el primer pago.
9. GO para prueba Live: comprador real independiente, cuenta legítima elegible, aceptación de renovación y autorización PayPal propias. No autopago ni test que simule al comprador. Verificar venta y merchant originales, firma, inbox procesada, ledger/período, cobertura/beneficios, agradecimiento único y revisión opcional. El regreso desde PayPal no basta. Documentar limitaciones de renovación mensual y cualquier operación adicional que requiera dinero/consentimiento.

## Pausa y recuperación

Ante incidencia, pausar nuevas compras e invitaciones mediante el panel protegido. Conservar funcionando worker, ledger y gestión/cancelaciones originales, sin liberar una intención incierta ni borrar evidencias. Inspeccionar GET/firmas de la generación original; no crear una segunda obligación. La resolución de incidentes exige revisar retenidos y salud; no es una liberación automática de holds financieros.

Para rollback de código, conservar nuevas tablas/metadatos y las pausas. Volver al artefacto previamente aprobado solo tras revisar compatibilidad: **no** reactivar automáticamente la campaña gradual ni recuperar EXECUTE de sus RPCs. Un worker anterior puede seguir conciliando y fallar de forma inocua al intentar mantenimiento gradual ya revocado; verificarlo antes de elegir ese rollback. Preparar una corrección forward antes de reabrir ventas. No DROP de funciones/datos en producción en este gate. El ensayo ROLLBACK del SQL completo ocurre exclusivamente en el laboratorio desechable.

## Repetir la verificación local

`npm ci`; `npm run verify:prepreview`; `npm run test:f18`; `npm run test:gradual`; `npm run test:f18:pg17`. Docker usa únicamente `pazo-f18-public-lab`, etiqueta `pazo.disposable=f18`, red none, sin puertos y base `f14_synthetic`; el runner rechaza otro contexto y jamás acepta una URL remota. Ese runner recrea solo su base sintética. Para navegador: instalar Playwright 1.56.1 en prefijo temporal, usar variables públicas **sintéticas**, Vite en 127.0.0.1:5188 y `npm run test:f18:browser`. El test intercepta todas las solicitudes externas y simula Auth/PayPal, conectando las RPC nuevas al PostgreSQL local. Ver workflow F18 para comandos completos.
